# S-001-阶段验收执行法

> 把"覆盖指引"级别的验收转成**可复跑、可抄证据**的实测，并在收官前完成交付物与规范的横向核对。

## 适用场景

- 阶段文档的"验收场景"条目已写清主张，但实现期的测试只做到"结构性/单元级"覆盖（例如主张是 N 路并发、端到端归因，而现有证据是单测 + 指引）
- 需要给非技术所有者一份"每条通过/未通过 + 证据在哪"的阶段报告
- 判别特征：报告里出现"留阶段验收执行""覆盖方式指引"这类字样

## 前置条件

- 六道门禁可一键跑绿（本仓库：`pnpm format:check && lint && typecheck && build && test && bash scripts/check-size`）
- 验收场景对应的 CLI/入口存在（本仓库 `keel scenario|replay|validate|hotswap|bench`）
- 阶段文档 §4 交付物表与 §5 验收场景表可读

## 步骤

1. **逐条分类**：把每条场景标成三种状态之一——已有实测 / 只有指引 / 一票否决且只有指引。**只对第三类动手补执行**，别重写已绿的项。
2. **给抽象主张找可执行口径**：主张里的形容词（"稳定""无污染""可归因"）必须落到一个可断言的量。例：
   - "缓存命中率稳定" → 把可见面序列化成**指纹**（升序 `name@version` 拼接），断言"未变更者跨轮恒定 + 变更者变化轮次严格等于自身剧本"
   - "完整决策序列可归因" → 断言 `seq` 从 1 **连续无缺**、插话**成对**留痕、依据编号只引用已发生事件、拒绝带齐归因字段
3. **规模级测试写成一个测试文件，不写成脚本**：真实进程 / 真实账本 / 冷实例复读；会话数等参数留一个环境变量口子供本机冒烟（默认值 = 验收口径值）。规模观测（耗时、并发数、常驻内存增量）用 `console.info` 打一行**证据行**，报告直接抄。
4. **复跑三次取逐项一致**：任何一次抖动就回去查是不是 flaky（规范 05 §5：flaky 即修或隔离，不许带绿灯收官）。
5. **横向核对交付物表**：逐条比对 phase 文档 §4 的代码/文档/其他清单——门禁只测体量与测试，**不测"该交的东西存不存在"**。空占位包、只有 smoke test 的交付物在这里才会被抓出来。
6. **坏消息先写**：报告按"已修复 / 登记限制 / 流程改进"三档如实登记，限制注明"不阻断验收的理由"和归属（回填清单 / 需 ADR / backlog）。
7. **门禁输出不入仓库**：证据抄进报告即可（规范 05 §5）；含本机绝对路径的行必须改写或删掉（规范 06）。

## 验证方法

- 报告里每条"通过"都能指到一个测试文件路径或一条 CLI 复跑记录（本仓库 `docs/design/phase-1/report.md` 的验收结果表即此形）
- 一票否决项逐条有实测（不是指引）；勾选状态与报告一致
- `bash scripts/check-size` 0 提醒；测试总数与报告披露数一致
- 规模观测行有数字（不是"很快/稳定"这类形容词）

## 失效条件

- 主张本身可以纯单测覆盖时不要上真实进程规模测试（成本高、收益低）
- 若阶段要求"性能达标"（阈值断言），本法不适用——那需要基准门禁而非验收补执行；本仓库 Phase 1 明确"只建测量不调优"
- 环境不具备多进程/多实例条件时（如受限 CI 内存），退化为"降低并发数复跑 + 报告注明口径"
