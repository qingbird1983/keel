# P-007 测试变绿之后：这一绿是真的吗

- 环境：2026-11-03 Phase 2 切片②施工，`tests/cordis-manifest-synthesis.test.ts`（真实子进程）与 `apps/keel/test/cli.test.ts`

## 现象

1. 三项真实子进程集成测试**全绿只花 161ms**——绿得可疑：直觉上"起子进程 + 两遍观察"不该这么快，怀疑根本没起舱、
   断言是在空数据上自证。
2. 另一头，一段新写的测试代码里手滑留下了一行自造的占位文本（`"X" === "" ? "" : "Y";`，语法就不成立），
   **直到跑该文件才暴露**——写完的当场没人看它。

## 根因

1. 快 ≠ 假：Node 26 的子进程起飞实测上百 ms，`pnpm build` 命中增量缓存约 1.5s，两趟观察各起 1~2 个舱，
   总量确实落在几百 ms 量级。**光看耗时判断真伪是不成立的**，得把事实打出来看。
2. 覆盖面的真相（本轮核实）：`packages/*/test` 与 `apps/*/test` **在各自 `tsconfig.json` 的 `include` 里**，
   由 `pnpm typecheck` 兜住；但 `pnpm build` 走 `tsconfig.build.json`（只管 `src/`），根 `tests/` 完全没有类型检查
   （已登记待办）。所以"只跑 build"看不到测试文件的错——**必须跑 typecheck**。

## 修复

1. 用一次性脚本直跑被测入口，把关键事实打印出来交叉验证（用完即删，不留在 `tests/`）：
   每趟的 `runId / 终态 / 轮数 / 事件数 / 事件类型集合 / 屏障是否放弃 / 候选名字集`。
   本次打印确认：pass 1 = `failed` + 16 条事件含 `AUTH_DENIED`×3，pass 2 = `halted` + 36 条含
   `TOOL_SCHEMA_CHANGED`/`TOOL_INVOKE`/`TOOL_RESULT`——子进程真起了，断言锚在真实产出上。
2. 手滑那行按当前文件内容重写并立刻 `prettier` + `eslint` + 跑该测试文件。

## 预防

1. **新写或大改测试文件后，顺序固定**：`prettier` → `eslint`（parse 级错误在这里就会响）→ `pnpm typecheck`
   （`apps/*/test`、`packages/*/test` 在其中）→ 跑那个文件 → 收尾时**全库 `pnpm test` 一次**，不要只跑改过的文件。
2. **断言要锚在"只能由被测行为产生"的事实上**：账本载荷字段、落盘文件内容、`name@version` 指纹——
   而不是"跑完了没报错"。子串断言另按 [P-006](P-006-真实子进程测试的时序屏障.md) 的教训精确化。
3. **绿得可疑时先取证再庆祝**：打印上表那几项事实的成本是几十行脚本、几秒钟，比事后怀疑整套验收便宜。
4. 覆盖缺口（根 `tests/` 无类型检查、`apps/*/test` 不在 build 里）继续按 Phase 1 报告 §8 的待办推进；
   在补齐之前，第 1 条的顺序就是替代品。

## 同源问题：红也要有证明力（2026-11-03 切片④）

"绿色要当场取证"的另一面是**红色也必须先于实现存在**，否则它证明不了主张。切片④的施工顺序偏离了设计稿 §8 的清单
（生产代码先写完，B4/B7① 两份验收测试是收尾时补的）：首轮跑红 7 条，逐条看全是**断言形状**写错
（真进程下轮号不是稳定量、装载拒绝会命中封闭集合里的两个码之一、`hooks` 置空与 `minItems:1` 互斥、注释里含 `CellClient` 字样）。
这些红**只教会我"我的断言写错了"**，一次都没能回答"实现是否满足主张"——因为实现已经在那儿了，测试是照着它写的。

- 与 [P-005](P-005-浮空close与Node版本差掩盖硬缺陷.md)、本条第 1 节同族：都是"结果的证据强度"问题，不是"结果对不对"问题。
- 处置：偏差如实写进 06 稿 §8（不追认成"先红后绿"），教训沉淀在此。
- 预防措施：**验收测试文件先建、先跑红、红因必须与主张对应，再动实现**——顺序写进每片设计稿 §8 清单的第一项，
  而不是散在"测试面"那节里；若因故做不到，就在 §8 明写"本轮没有红测保护"，让评审看得见缺了哪一层证据。
