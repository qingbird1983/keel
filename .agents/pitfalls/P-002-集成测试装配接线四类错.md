# P-002 集成测试装配接线：五类错（参数位、顶层捕获、定位法、dist 解析、并发重建抢产物）

- 环境：切片④ A3/A4 集成测试（tests/ 真实进程）
- 症状：三组失败同根——①`serveCellChannel(conn, binding)` 漏传第三参 deps → `deps.tracker` 读 undefined；②`new CompensationExecutor({ledger, factory, onAlert})` 把 opts（onAlert）塞进 deps（第一参）→ 告警缝永不触发；③补偿执行器在**模块顶层**构造，捕获的 `ledger` 尚是 beforeAll 前的 undefined → sweep 一调即 TypeError（被调度器吞成 false → RUN_FAILED，表象远离病灶）

## 规则

1. **多参构造/工厂函数，先读签名再接线**——deps（依赖组件）与 opts（行为选项）是两个参数位；字面量里塞错位置不报错、静默失效。接线后先跑一条"最小正路径"探针确认参数真的到达。
2. **凡依赖 beforeAll 初始化的组件，一律在 beforeAll 内构造**；模块顶层 `const x = new X(deps)` 捕获的是 import 时刻的 undefined。jest/vitest 的 hook 时序不会拯救模块初始化序。
3. **失败表象远离病灶时的定位法**：错误被中间层吞掉（boolean 化、catch 化）时，直接 dump 账本/事件流看"哪个事件没发生"，从缺失事件倒推第一个断点——比读调用栈快。
4. **跨包 import 走 dist**：`tests/` 里 `import {x} from "@keel/foo"` 解析到 `packages/foo/dist`，改完 `src/` 不重新 build 就得到 `x is not a function`（或导出面为空）——先 `pnpm build`（或 `pnpm --filter <pkg> build`）再判"代码写错了"。包 `exports` 指向 dist 是设计（发布面 = 构建产物），不是坑位可改。

5. **构建只有一个合法位置：`vitest.config.ts` 的 globalSetup**（`tests/fixtures/global-setup.ts`）。
   第 4 条的"先 build 再判"曾经在 11 个测试文件里各写一遍 `execSync("pnpm build")`——切片② 门禁实测（`pnpm clean` 起全链）：
   41 个 worker 并发重建，互相抢同一批 `dist/` 产物，其中一个拿到 `ERR_PNPM_RECURSIVE_RUN_FIRST_FAIL`，整套验收**随机红**。
   现在主进程串行构建一次再开 worker：freshness 与规则 4 都保住，竞争面消失；测试文件里不再出现构建调用。

## （复发记录）同类问题的新载体

- **2026-11-03 切片④：同一个坑换到了测试夹具身上。** rig 里 `new Scheduler({ledger, auth, budget, ctx, hooks, gateway, delay})`
  ——`delay` 是 `SchedulerOptions`（第二个参数位）的字段，塞进 deps 之后**不报错、不生效**：注入的重试退避根本没被采纳，
  测试表现为"卡 30 秒 ×3 然后超时"，而失败信息是 vitest 的 `Test timed out`，离病灶两百行远。
  三点教训：
  1. 规则 1 不只适用于生产接线——**测试夹具的构造同样先读签名**；夹具是"被测系统的一部分"，它静默失效会把主张变成玄学。
  2. 根 `tests/` 没有类型检查（[P-007](P-007-测试绿色要当场验真.md) 登记的覆盖缺口），这类"对象字面量多写一个字段"的错
     **编译器本来能抓**，是我们的检查面抓不到——补齐之前，别指望 `pnpm typecheck` 兜住 `tests/`。
  3. 预防措施升级：**给每个"应该到达的选项"留一条可断言的缝**。这次在 rig 里把注入的 `delay` 记成 `retryDelays`，
     B7① 直接断言 `[30_000, 30_000, 30_000]`——它既是"内核钳制策略退避"的主张证据，也是"选项真的到达了"的探针。
     以后凡在夹具里传 opts，都按这个形状留一条断言，而不是靠"跑通了"。

- **2026-11-03 Phase 3 切片②：内核改动让潜伏了三个切片的接线缺陷集体显形。** 默认入口开始装载期发布静态工具
  （03 稿 F4 处置）后，"装载期必有 Cell→宿主请求"成了硬前提，此前零请求时看不见的接线错全部爆雷：
  ① `serveCellChannel(conn, binding)` 漏传 deps（第 1 条原样复发，同一个文件 cell-crash）；② deps **残缺**
  （只传 `{ledger, tracker}`，缺 auth/ctx——发布走到 `deps.auth` 即 TypeError → BADFRAME → 舱装载即死）；
  ③ **spawn 与 serve 之间被 await 隔开**（恢复路径 `await cell.migrate()` 插在中间——发布帧先到，`no serve handler`）。
  教训：
  1. 规则 1 的面扩大了：**漏传/残缺/晚挂三种形**都要查；残缺尤其隐蔽——对象少三个键不报错，等第一次用到缺的键才炸。
  2. **装配次序升为硬约束：`spawnCell` 之后、任何 await 之前必须挂好 serve + alloc**（装载义务含发布后，
     装载期即有跨进程往返；03 稿 §4.5 登记）。
  3. 内核行为收紧会**暴露存量测试的潜伏缺陷**——这不是回归，是把"靠运气绿"变成"靠机制绿"；处置时按
     P-007 当场验真的口径核对失败的真实原因，别急着改内核。
