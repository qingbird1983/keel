# P-022 profile 全家桶下补偿权限只读第一条装配记录

## 现象

Phase 4 切片④的真进程用例里，`file-write` 排在 profile 第三个插件（model → engine → file-write）：
写入成功、`EFFECT_SETTLED` 带 `created:true` 收据，但补偿执行器 `compensate(ref,{mode:"run"})`
返回 `false`，并留下 `COMPENSATION_ESCALATED`——`fs.remove` 三次都被判"路径不在 allow 内"。
同样的 file-write 单件装配（Phase 3 B-E1）一切正常。

## 根因

`CompensationExecutor.readPermissions` 只读本 run 的**第一条** `ASSEMBLY_RECORDED` 载荷：

- 单件路径：run 只有一条装配记录，恰好就是能力插件，权限读得到；
- profile 路径（01 稿 P6）：**逐插件一条**装配记录，第一条是 model（`permissions: []`），
  能力插件的 `fs.write.allow` 在后面的记录里——于是内建 `fs.remove` 拿到空 allow，必然升级。

装配记录"从一条改为多条"时，所有"只读第一条"的读者都得重新核对；这条只在全家桶下暴露。

## 修复

`readPermissions` 改为分页读本 run **全部** `ASSEMBLY_RECORDED`，合并各条的 `permissions`
（按 `cap + allow` 去重）。语义不变：仍是"本 run 声明过什么"，不是"某个插件声明过什么"。

## 预防

- 账本事件从单条变批量时，先搜所有按类型取 `events[0]` 的读者（`grep "ASSEMBLY_RECORDED"`）。
- 补偿/恢复类断言必须至少有一条**多插件 profile** 的用例；单件夹具会掩盖这类读取假设。
- 回归锚点：`tests/engine-kind-e2e.test.ts` D3-b（真写盘 → 只读账本补偿删除）与 D3-c
  （崩溃后补偿回放），以及 `tests/native-file-write-e2e.test.ts` B-E1~E5（单件路径不退化）。

## 证据

修复前：D3-b `expect(compensate(...)).toBe(true)` 收到 `false`，账本出现
`COMPENSATION_ESCALATED`；修复后 D3-b/D3-c 绿，文件按收据删除，单件 B-E1~E5 保持绿。
