# P-008-舱在装载屏障期死亡，违规表却是空的

> 单篇 ≤ 80 行；新增前已检索 P-006（时序屏障）——本篇是**屏障放弃之后的死亡归因**，与 P-006 互补，不重叠。

## 现象

Phase 2 切片③ 的 B3 集成测试里，一个两作用域传递的样本 run：

- `expect(probe.violations).toEqual([])` **通过**；
- 下一条断言 `lastResult(events, "note.new").resultDigest` 报 `expected undefined to deeply equal { token: 'TK-42' }`；
- 翻账本才看清：整条 run 只有 `ASSEMBLY_RECORDED / RUN_STARTED / … / AUTH_DENIED ×2 / RUN_FAILED`，**一条 `TOOL_RESULT` 都没有**，`probe.seen` 是空数组、`barrierGaveUp` 是 `false`。

表面像"工具没返回结果"，实际是"舱在装载阶段就被内核拒了注册、整个 run 在屏障期就死了"。

## 根因

两层：

1. **策略主体不匹配**。rig 用 `policyFor(legacyManifest(caps), AGENT)` 编译授权规则（规则里的 `subject` 是写死的 `"agent-b3"`），而 `runLegacy` 把 `subject = scope.agentId` 发给内核。那次样本为了"两个域"把 `agentId` 换成了 `agent-producer` / `agent-consumer` → 规则匹配不上 → `tool.register` 被拒 → 承接层入口的 activation 抛出 → 舱非零退出。
   跨域本来就该靠 **scope（`sessionId`）**分开，不是靠换授权主体。
2. **rig 的归因缺口**（本篇要沉淀的那条）。driver 在装载屏障未满足时**不执行 plan**：既不做 `visible/absent` 检查，也不 `seen.push`。于是 run 死亡时 `violations` 保持空表——测试把所有"前置期望"当成满足了，然后在后面的断言上以一种看不出因果关系的方式失败。

## 修复

- 测试侧：两域改回同一 `agentId`、不同 `sessionId`，并**先断言终态**（`expect(status.state).toBe("halted")`）再断言账本内容。
- rig 侧（永久修复，覆盖所有后续样本）：`probe.done` 收口时补一条违规——

  ```ts
  probe.done = started.done.then((st) => {
    if (barrier && st.state === "failed") {
      probe.violations.push(
        `run ${spec.runId} failed while the activation barrier was still up (reason=${st.reasonCode ?? "?"})`,
      );
    }
    return st;
  });
  ```

  位置：`tests/fixtures/cordis-rig.ts`。只针对"屏障仍未满足 + 失败终态"这一组合，`boot: []`（不等）与 `barrierGaveUp`（已按证据放弃）两条既有路径不受影响，全库 338 测试复跑无新增红。

## 预防

1. **写多作用域样本前先问一句：作用域靠什么分开？** 靠 `{agentId, sessionId}`（分区是 scope 级）；`agentId` 一换就换授权主体，必须同步换策略——rig 的策略是按单一主体编译的。迁移手册 §4 已把这条写进注释与文档。
2. **断言顺序纪律**：真实进程测试的第一条断言是**终态**（`state`/`reasonCode`），第二条才是账本内容。终态不对，后面所有"没结果"的断言都是同一件事的回声。
3. **rig 必须是会说话的**：任何"跳过检查"的分支（屏障、放弃等待、负例路径）都要把跳过的理由落成一条可断言的事实，否则测试绿得不明不白。同 P-006 的"放弃等待写成证据"是同一条纪律的另一半。

## 归属
