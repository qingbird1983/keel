# P-009-跨边界序列化会静默丢掉东西（而不是报错）

> 单篇 ≤ 80 行；已检索 P-004/P-005（构建产物与释放）——本篇只管**"值穿过序列化层之后少了一块"**这一族，两者不重叠。

## 现象

同一族两个实例，都发生在 Phase 2 切片⑤，都是**单测全绿、真进程才露出来**：

1. `snapshot()` 返回 `{ ticks: 1, onSave: fn }`，落盘"成功"，新进程挂载后拿到的是 `{"ticks":1}` —— 没有报错，字段自己没了。设计稿写的是"不可序列化即抛"，实现按那句话去信任 `JSON.stringify` 就漏了。
2. 舱内 `client.modelStreamStart(...)` 遇到上游失败，catch 到的错误 `err.code` 是对的（`GATEWAY/UPSTREAM-ERROR`），但 `err.detail` 是 `undefined` —— 断流口径要求"失败前给了几片、结了多少钱"能穿回舱内，主张直接落空。测试断言 `expected null to be 'STREAM_UPSTREAM_THROW'`。

## 根因

**序列化层的默认行为是"丢"，不是"拒"，而且两处丢法都不属于本包类型系统能看见的范围。**

1. `JSON.stringify` 只对**循环引用**抛 `TypeError`。函数、symbol、`bigint` 在对象里被**静默删除**（在数组里变成 `null`）；`undefined` 也删。所以"不可序列化即抛"这句话在标准库里根本不成立。
2. `toFrameError(err)` 当时写成 `if (err instanceof ChannelError) { …保 detail… }` 再兜底。`@keel/core` 的 `KeelError` **不是** `ChannelError` 的实例（本包不依赖 core，跨包错误类永远认不出），于是走兜底分支——兜底只取 `code` 和 `message`，`detail` 直接掉在地上。跨包边界的错误识别只能靠**结构**，不能靠 `instanceof`。

## 修复

1. `packages/host/src/snapshot.ts`：`guardUnrepresentable` 作为 `JSON.stringify` 的 replacer，遇到函数/symbol/`bigint` 主动抛（循环引用仍由 `JSON` 自己抛）。`undefined` 按 `JSON` 语义仍是丢弃——这是格式的形状，如实写进 05 手册 §9 与 07 稿 §10，不假装解决。
2. `packages/cell-runtime/src/protocol.ts`：`toFrameError` 改成**结构取码**——`typeof err.code === "string" ? err.code : "CELL/INTERNAL"`，`detail !== undefined` 就随帧带过去，不再按类分支。形状仍是 `{code, message, detail?}`，零新字段。

## 预防

- **写"序列化/落盘/跨进程"相关断言时，先问一句：标准库在这种情况下是抛还是丢？** 只要答案是"丢"，就必须显式加守卫并配一条"丢了要红"的测试。
- **跨包错误体一律按结构识别**（`code`/`detail` 字段），不要在 A 包里 `instanceof` B 包的错误类——这类判断永远只在同包内成立。
- 固化位置：`packages/host/test/snapshot-store.test.ts`（"不可表示值即抛且什么都不写"+ "null/undefined 状态不写文件"）与 `packages/cell-runtime/test/protocol.test.ts`（KeelError 形状的 `detail` 照常穿帧 + 无 detail 时不写这个键）。
- **观测位纪律**：序列化层的坑只有真进程测试能看见。任何"跨通道返回值/错误体"的主张，至少配一条真进程断言，不能只靠同进程单测收口（本篇两条实例都是单测全绿之后红在真进程上）。
