# P-011-中文文案里的 ASCII 双引号会截断字符串（同族：`it("…）"` 标题）

> 单篇 ≤ 80 行；已检索 P-002/P-006/P-007/P-008/P-009——本篇管的是**写测试/夹具时的字面量语法坑**，与上述条目不重叠。

## 现象

同一片施工里两次写下这种标题（第二次是刚改了第一次的教训之后）：

```ts
it("llm 命名空间的未知成员也有去处（…就是一种"没交代"）", () => {
```

`"没交代"` 里的第一个 ASCII `"` 直接闭合了字面量，后面跟着裸中文 → **整个文件解析失败**，一条用例都收集不到。信息形如 `Unexpected token` / `Expected ',', got 'ident'`，长得像工具链配置问题，不像"我引号打错了"。

两次都是在**重读自己写的文件**时发现的（不在门禁里）：切片⑤那次是 `tests/snapshot-cross-host.test.ts` 写完先读回；本轮那次是 `packages/cordis-adapter/test/index.test.ts`。如果放着不管，暴露点会是 lint 的 fatal parse error 或 vitest 的收集阶段，而不是断言层。

## 根因

中文行文习惯用引号强调，而 `“…”` 与 `"…"` 在编辑器里看起来一样。写进 `it("中文标题")` 这种**双引号字符串内部**时，ASCII `"` 直接闭合字面量，后面跟着的是裸中文 → 解析失败。

三点让它反复咬人：

1. 中文正文里"引号"是**默认书写**，不是特例；
2. 测试标题是文档，越写得清楚越容易加引号；
3. 根 `tests/` 不进类型检查（P-007 记过的那条缺口），语法错只在 vitest 收集阶段暴露。

## 修复

- 测试标题与注释里的强调一律用直角引号 `「…」`（ASCII 字符串安全，中文可读）；
- 已经存在的两处改成 `「」` 后重新收集，红点回到真正该红的断言上。

## 预防

**写完/改完 `tests/**` 与 `*test.ts` 立刻跑这条机械检查**（一行命令，命中即改）：

```bash
for f in $(git diff --name-only HEAD | grep -E '\.(ts|mjs|cjs)$'); do
  awk -F'"' 'NF>3 && /it\(|describe\(|test\(/ {print FILENAME":"NR": "$0}' "$f";
done
```

- 判据：一行里 ASCII 双引号**多于 2 个**且该行是 `it(` / `describe(` / `test(` → 十有八九是标题里嵌了引号；命中后人工看一眼，确属强调就换 `「」`。
- **落笔时的替代写法**：`it()` 标题与字符串型注释里的强调统一用直角引号 `「…」`；ASCII `"` 只当语法用，不进中文正文。
- 为什么不能靠 prettier：`prettier --check` 对**解析不了**的文件报的是解析失败，容易被当成格式问题跳过去。
- 门禁能兜住但定位慢：`pnpm lint`（覆盖 `tests/`）会报 fatal parse error，`pnpm test` 会在收集阶段整文件失败——两者都只告诉你"这个文件读不懂"，不告诉你"是标题里的引号"。`pnpm typecheck` **不覆盖根 `tests/`**（Phase 1 报告 §8 记的缺口），指望不上。
- 上面那条检查命令的作用就是**把定位从"门禁阶段"提前到"写完那一刻"**：它只查刚改过的文件，命中即人工看一眼，成本一条命令。
- 顺手纪律：**测试标题里的引号形状不是审美问题而是语法风险**；夹具 `.mjs` 同理（`//` 注释里随便用，字符串里别用）。
