# P-010-给旧原语加新语义，旧调用点的"前提"就消失了

> 单篇 ≤ 80 行；已检索 P-006/P-008（时序与死亡归因）——本篇管的是**"借来的原语"在语义升级后不再表达原意图**这一族。

## 现象

Phase 2 切片⑤ 把 B7③（drain 的确定次序）落进 `Supervisor.drainAndReap()` 之后，一条**从没被本片碰过的** Phase 1 验收测试红了：

```
FAIL tests/cell-crash-recovery.test.ts > A3（V3）
AssertionError: expected { seq: 38, round: 5 } to match object { round: 2 }
```

`keel scenario a3` 同样从 `checkpoint round=2 / pending=2` 漂成了别的数字。表面看像"drain 把恢复搞坏了"，而且是全库 431 条里唯二相关的两条。

## 根因

**旧代码里 `drainAndReap()` = `halting → kill() → reaped`，它其实只是"硬杀"的包装**。A3 与场景 a3 想表达的前提是"**动作在途时被打断**"，于是借了这个名字——因为在途时它确实会立刻把进程打死。

B7③ 把 drain 定义成 **拒新 → 等在途收束 → 宽限到期才强杀**。语义升级后，那条 `tool.exec` 会正常返回、轮照常收束、run 继续往下跑几轮才死 —— A3 需要的"未决效果清单"根本没被制造出来（清单从 2 条变成"全收干净"）。

所以红的不是实现，是**测试的前提**：前提所依赖的原语，含义已经被这次改动正当掉了。

## 修复

1. 把"硬中断"这个原语公开：`SupervisedCell.kill()` 从 `private` 转为公开方法，文档写清它与 `drainAndReap()` 是**两件事**（失控看门狗走的同一条路；日常收束用 drain）。
2. 两处调用点改 `await cell.kill()`，注释从"kill（受控 → killed 分类）"改成"**硬中断**：a3 的前提是在途被打断"。
3. 断言原样不动，跑出来与 Phase 1 记录逐字一致（`checkpoint round=2 / pending=2 / snapshot v1@round1`，`scenario a3: PASS`）。

关键判断：**没有改一条断言**。如果反过来去把 A3 的期望改成 round=5，就等于把"在途被打断"这条主张悄悄换成"收尾收得挺干净"——一票否决项 A3 的语义会被自己稀释掉。

## 预防

- 升级任何**公共原语的语义**（尤其是名字里带动作意味的：`dispose` / `drain` / `close` / `cancel`）之前，先 `grep` 全部调用点，逐条问："**这个调用想要的是新语义，还是旧的那个动作？**"
- 测试与场景复演借原语表达"前提"的地方最多。判据：注释里出现"（受控 → killed 分类）""模拟中断""跑到这里就 kill"这类**意图说明**的调用点，几乎都不是要新语义。
- 若答案是"它们要的是另一个动作"，就把那个动作**做成公开原语**，而不是给旧原语加一个 `force: true` 参数（参数开关会让"什么时候该传 true"变成新知识）。
- 固化位置：`tests/cell-crash-recovery.test.ts`（A3 前提）与 `apps/keel/src/cmd-scenario.ts`（交付入口复演）各一处，二者都断言 `pending` 条数与快照轮次——drain 语义若再变，这两条会立刻指出"前提没了"。
