# P-006 真实子进程测试：把两段真实时序压成一个 tick

- 环境：2026-11-03 Phase 2 切片①施工 C，`tests/cordis-adapter-tier-a.test.ts` 首次落地（9 项里 8 项红）

## 现象

- 单元级全绿：host 的 `cell-server` 用例证明 `tool.register` 会写内核分区、无规则会拒；adapter 的 `cell-port` 用例证明两半提交与回滚。
  真实进程那层却一律红：`round 1: expected visible "echo", got []`——**可见表恒为空**。
- 隔离调试（临时把子进程 stderr 接出来 + 起 run 前睡一下）暴露真相：整轮测试只花 24ms，而子进程起飞要上百 ms。
  睡过 1.5s 之后同一条链路一次通过（三笔注册 → 分区 → 首轮 `TOOL_SCHEMA_CHANGED` 三条）。**代码没错，是时序被压扁了。**

## 根因

1. 调度器的轮次没有 I/O 等待，一轮是亚毫秒；`spawn` 之后 run 立刻跑完，舱内连插件模块都还没 import。
   生产里"装配就绪 → 才起 run"是两段真实时间，测试把它们焊成了同一个 tick。
2. 断言式 driver（只从内核送进来的可见表选工具）是**这条红灯的来源**，也是它的价值：
   Phase 1 的脚本 driver 直接点名工具，同样的接线缺口当时看不出问题（02 稿 §2 F1 的正面解法）。
3. 契约里没有"activation 完成"的信号：事件帧在 §3.1 有定义但 MVP 无推送方。
   顺手加第三个 op 或让舱内反向推一帧，都越出 ADR-0010 授权的范围 → **不动协议，改测试的时序假设**。

## 处置（只用既有信号）

- 屏障放在 **driver 里**而不是 `scheduler.start` 之前：run 必须活着经历舱的生死。
  起在 start 之前会有两个负例路径变成假证据——"未报关被拒 → 舱崩 → `RUN_FAILED{CELL/CRASH}`"观察不到（run 还没起），
  `tierA-04` 的崩溃同理（等不到退出就只能对着死舱起一个 run）。
- 两种入口各用自己的可观测凭据：旧入口 = 内核分区里出现 activation 注册的名字（分区写只能来自注册帧）；
  默认入口 = 一次 `tool.exec` 探测拿到应答（`cell-runtime/main.ts` 在动态 `import` **之后**才 `startCell`，
  且静态工具同步登记完才回到事件循环，所以第一个应答必然来自"插件已装载"的舱）。
- 放弃等待的两个条件都写成证据而不是掩盖：`cell.phase === "exited"` / `conn.isClosed` / 超过截止 → 记 `barrierGaveUp`，
  然后**照原计划继续**，让违规与账本自己说话。
- 空转轮不计入 `seen`，断言计划的轮次语义不被等待污染；账本顺序断言要锚在**因果事件**上
  （`late` 的变更排在 `grow` 那次 `TOOL_INVOKE` 之后、下一次决策之前），不能锚在"第 1/2 个 DECISION"上。

## 顺带堵掉的三个同源陷阱

1. **`pnpm format` 会把样本文件改成仓库风格**（单引号→双引号）。这批文件的书写风格是被测对象的一部分，
   真样本到位后一次全库格式化就会静默毁掉"一行没改"的证据 → `.prettierignore` 长期排除 `tests/fixtures/cordis-plugins/`。
2. **子串断言会误伤**：`JSON.stringify(events)).not.toContain("sum")` 被每条 `DECISION` 的 `summary` 字段命中。
   跨舱"看不到对方"的断言要按 `"tool":"sum"` 精确匹配，或直接取结构化工具名列表比对。
3. **scope 分区不按 run 归零**：同一 scope 的第二个 run 里，只等"名字存在"会在上一 run 留下的旧版本上立刻满足，
   把"本舱注册到了 v3"等成"分区里早就有 flip" → 屏障条目写成 `name@version`，跨 run 连续性同时成为正面断言。

  → 新增第 4 条预防。

## 预防

1. 真实子进程测试的红，先问"**被测的那一端真的起飞了吗**"，再怀疑被测逻辑：把子进程 stderr 接出来 + 单跑一次带延时，
   比在断言里加等待更快定位（诊断文件用完即删，别留在 `tests/`）。
2. 跨进程写状态的链路，测试侧要显式写出"就绪"这一段；没有正式就绪信号时，**登记成设计稿的限制条目**（02 稿 §12 第 5 条），
   不要用固定 `sleep` 蒙过去——固定延时既拖慢门禁又会在慢机器上随机红。
3. 观察"异步事件是否只伤本舱"时，崩溃/退出必须发生在 run 存活期间：给断言计划加一步"等舱退出再收束"，
   而不是赌调度循环跑得比退出通知快。
4. **一条测试只留一个失败原因**：同一次装载里若并存两条失败（权限被拒 → 未决拒绝 → 舱崩，与迁移钩缺失 → 调用报错），
   谁先到达不确定，断言会随平台翻脸。不相干的那条用策略或材料排除，让失败路径唯一；
   它自己的正面覆盖留给本来就该测它的那一条线（切片② 里 B6② 与 B2③ 的分工就是这么切的）。
