## 0. 现状核对（带证据，本合同的全部前提）

- **F1 会话只是信封里的一个字段**：事件信封有 `sessionId`（`packages/core/src/events.ts:90-99`），但没有任何"会话"对象、索引或读取面；会话身份 = `(agentId, sessionId)`，今天只体现在目录层级。
- **F2 布局已经支持多 run，但顺序无定义**：账本路径是 `<root>/<agentId>/<sessionId>/<runId>/seg-NNNNNN.jsonl`（`packages/core/src/ledger.ts:4`），`seq` 只在 run 内单调（同文件 :8）。run 目录名是随机串（`package-run` 入口 `run-${randomUUID().slice(0,8)}`，`apps/keel/src/cmd-run.ts:101`），目录扫描给不出可靠的先后次序。
- **F3 两条入口的会话现状不一致**：单件路径把会话设成 `sess-${runId}`（`apps/keel/src/runtime.ts:427`），即 **session ≡ run（1:1）**；profile 路径缺省 `sessionId:"main"`（`packages/host/src/profile/assemble.ts:140-142`），所以同一数据目录里多次 `keel run --profile` **已经落在同一个会话目录下**——但彼此之间没有任何会话语义（不共享历史、无顺序、无并发约束）。
- **F4 跨 run 读取面为零**：`ledger.read` 的过滤键必填 `runId`，模块注释明确"跨 Run 全量读取暂不开放"（`packages/core/src/ledger.ts:11,47-52`）；同一 run 不允许第二个写者，重开已有 run 一律拒绝（同文件 :9、:279-286），恢复/延续统一走新 `runId`（契约 §4.5）。
- **F5 恢复已经有骨架，但"接着干"没有历史**：`RecoveryManager` 的顺序是"补偿闭环 → 快照挂载 → 以新 runId 延续"（`packages/host/src/recovery.ts:84-113`），`keel recover` 也确实在同一会话下开新 run 并写 `RUN_RECOVERED`（`apps/keel/src/cmd-recover.ts:79-102`）；但新 run 的模型视图是空的——没有跨 run 表面投影，也没有 `turnInput`。`mountState` 只是 Cell 自己的状态，不是对话。
- **F6 会话级预算不跨 run / 不跨进程**：`Budgeter` 的 session 已用量是内存字段 `ScopeState.sessionUsed`（`packages/core/src/budget.ts:43-46,61-62`），新进程即归零；而 `BUDGET_RESERVED` / `BUDGET_SETTLED` 载荷里已经有 `sessionRemaining`（`packages/core/src/events.ts:212-232`）——事实在账本里，只是没人投影回去。
- **F7 压缩只有预留形状**：`SurfaceOp {kind:"compress"|"redact", fromSeq?, toSeq?, note?}` 已定义但**不实现**（`packages/core/src/events.ts:356-365`；ADR-0021 决策 4），表面白名单封闭三类（同文件 :81）。`PageStore` 的换页是另一件事（`packages/core/src/page-store.ts`），不能当压缩用。
- **F8 投影函数本身已经跨 run 可用**：`projectSurface(events)` 只吃事件数组、只按白名单（`packages/core/src/surface.ts:45-85`），不看 runId——缺的是"从哪拿事件、按什么顺序拼"，不是投影算法本身。

> 结论：本阶段不是"发明会话"，而是**把已经存在但互不相连的四块（目录布局、表面投影、恢复器、会话预算）接成一条真会话**。

> 修订（2026-11-04，切片①设计稿回填）：压缩命令由独立的 `keel compact` 并入 `keel run --compact`——账本 append-only 且拒绝向已终结 run 追加，独立命令无处落标记（见 [03 稿](../design/phase-5/03-compaction.md) §4 与 [04 稿](../design/phase-5/04-contract-revision.md) C5）。CLI 清单同步修订。

## 1. 目标

Phase 4 的闭环有一个硬边界：**run 一结束，上下文就死掉**。追问、纠错、跨天协作、长程任务全部做不到；README 里"长程任务可从一致点恢复"目前只对"同一个 run 的崩溃"成立，对"会话"还不成立。

本阶段把会话从信封里的一个字段，长成**一等事实**：同一会话的多次 run 共用一条可重算的模型视图；进程被杀能接着干；上下文变长能压缩，而账本一条不少。

一句话验收：**同一会话跑三次，第三次的模型知道前两次说过什么、做过什么；中途杀掉进程，重启后接着干；上下文超长时压缩生效，原始账本与归因完整。**

方向口径（所有者 2026-11-04 会话确认）：只做会话本身；fork/回滚、留存删除、UI、多 Agent 不在本阶段。**流向优先于结构**：三份设计稿先钉数据流向（谁写、跨哪些边界、每跳账本记什么、谁有权读、坏了算谁的），再写结构。

## 2. 范围

### 做

- **会话流（session stream）**：会话级读取面（跨 run 事件流 + 复合游标）、run 序号（会话内单调）、单活约束（同会话同时最多一个 run）、`keel run --session <id>` 续跑、`keel sessions list|show`
- **跨 run 表面投影**：投影升版，输入改为会话流（run 序 + run 内 seq），输出同一会话的模型视图；跨进程重算结果一致；白名单与 `SURFACE_PROJECTION_VERSION` 纪律不变
- **续跑与崩溃恢复的统一入口**：正常续跑 = 前一个 run 终态后追加输入开新 run；崩溃恢复 = 既有 `RecoveryManager` 顺序（补偿 → 快照挂载 → 新 run）之上，接会话投影历史；两条路都产出"新 run + 会话历史 + 会话序号"
- **会话预算连续性**：session 级已用量从账本投影（`BUDGET_*` 的 `sessionRemaining`），宿主重启 / 新进程不归零；耗尽处置沿用契约 §4.3
- **压缩（compaction）首版**：落地 ADR-0021 预留的 `surfaceOp`（或等价新事件，见 §8 K4）；摘要生成走既有模型 seam（一次受治理调用：预算/超时/失败收束）；投影按压缩区间折叠；**原始事件永留、视图可还原**
- **可观测与门禁**：会话读取的 scope 收窄机械断言；会话流 / 压缩的基准段（只测不设阈值）；CLI 冒烟

### 不做（明确排除）

- **fork / 回滚 / 任意 seq 开子会话**（DSH 的回滚替代物）——backlog
- **留存删除、段 GC、冷归档**——本阶段只定观测与阈值，不删一个字节
- **压缩的自动调度策略**（换模型触发、overflow 恢复触发）——首版只做手动 + 阈值（阈值来源见 §8 K4）
- **`kind:"ui"` / 桌面壳 / 任何 UI 场景**——下一阶段（本阶段验收不锚 UI）
- **多 Agent / subagent / 委派谱系**——backlog
- **跨 agent 共享记忆、跨会话检索**——与架构 I5 冲突，不动
- **会话导出 / 迁移格式（ACP/SDK 形态）**——backlog
- **真实模型进 CI**——压缩摘要继续由 mock 承载全部断言
- 补偿语义、策略 hook 词表、manifest kind、禁面规则集——无新需求不动（除 §8 K6 点名项）

## 5. 验收场景（定稿：只留验证五大不变量的条目）

> 标注【一票否决】的场景未通过时不得打 `phase-5.end` tag。每条注明锚定的不变量；不锚不变量的业务场景一律不进本表。

- [ ] **E1【一票否决】跨 run 会话续跑（I3 / I1）**：run1 正常终态 → 同一会话开 run2（新进程），run2 的模型视图包含 run1 的用户输入、模型回答与工具结果（`toolCallId` 配对正确）→ run2 只追加本次输入，不重放旧事件 → 同一账本在两个独立进程里重算投影，结果逐字节一致。
- [ ] **E2【一票否决】崩溃恢复接会话（I2 / I3）**：run 在"文件已写、模型还在想"时被强杀 → 恢复入口按既有顺序（补偿闭环 → 快照挂载 → 新 run）→ 新 run 的历史含崩溃前已结算的表面事件，未决效果零悬空，补偿可回放；另一并行会话不受影响。
- [ ] **E3【一票否决】压缩不改事实（I3 / I1）**：触发压缩 → 摘要来自一次**受治理**的模型调用（有 `MODEL_INVOKED`/`MODEL_USAGE`、计费、超时与失败收束，无旁路调用）→ 投影折叠被遮蔽区间，治理事件不进摘要输入 → 原始事件仍全部在账本、完整可读 → 以"忽略压缩"的投影模式重算可还原未压缩视图。
- [ ] **E4 会话隔离（I5）**：会话读取按 `(agentId, sessionId)` 收窄，越界读取被拒（机械断言，零泄漏）；不同会话的投影互不可见。
- [ ] **E5 会话预算连续性（I1 / I3）**：配置 session 限额 → run1 消耗 → 进程重启后 run2 的已用量包含 run1（来自账本投影）→ 耗尽按契约 §4.3 处置，不因新进程而归零。
- [ ] **E6 顺序与并发（I1）**：同会话并发第二个 run 被拒且**零写入**；run 序号会话内单调、落账本；不同会话并发互不阻塞。
- [ ] **E7 质量与回归**：六道门禁全绿；Phase 1~4 承载测试（三件套 e2e、cell-crash、audit-attribution-replay、throughSeq、快照跨主机、model/engine e2e）零退化；新增代码零三方运行时依赖；体量哨兵绿。

## 6. 设计稿必答问题（切片①设计稿须逐条回答并留痕）

- **S1 会话流的形状与定址**：会话流 = 按什么顺序拼接各 run？跨 run 定址用复合键 `(runId, seq)` 还是别的形状？既有 `basedOn` / `throughSeq` 的 run 内口径如何不被破坏？（→ ADR-0025）
- **S2 顺序与单活**：run 序号谁分配、落在哪（`RUN_STARTED` 载荷 vs 独立索引）、崩溃后如何续号？单活用进程内互斥还是跨进程租约（锁文件 `O_EXCL` + 过期）？拒绝时写什么事件、错误码是否零新增？（→ 01 稿）
- **S3 跨 run 投影**：拼接顺序与截断策略；`toolCallId` 跨 run 的唯一性；`surfaceOp` 区间的跨 run 定址；投影版本号与重算；上下文从哪里开始（最近 N 个 run 还是全量）？（→ 01 稿）
- **S4 会话预算的账本投影**：`sessionRemaining` 的正确性（预扣在途、失败退款、超支夹取）；内存态与投影态的权威关系；恢复时机（启动时一次 vs 每次结算前）？（→ 01 稿）
- **S5 续跑与崩溃恢复的分界**：前一个 run 有终态 = 续跑，无终态 = 恢复；两条路共用哪些部件、`RecoveryManager` 的复用边界在哪；恢复后 `turnInput` 与历史如何合成；engine 驱动的恢复怎么接？（→ 02 稿）
- **S6 压缩语义**：事件形状（`surfaceOp` on `TURN_INPUT` vs 新增表面事件）；摘要调用走哪个模型（同模型 / 专用摘要模型）、预算与失败如何收束；折叠算法（区间、嵌套压缩、幂等）；"忽略压缩"的还原模式；摘要内容不得包含治理事实的机械校验？（→ 03 稿 + ADR-0026）
- **S7 存储面与体量**：会话索引是否物化（目录扫描 vs 索引文件）；读取分页与按类型过滤；压缩后的账本体积与 DeepSeek KV cache 前缀断裂的成本观察；保留策略只定阈值不删（→ 01/03 稿）
- **S8 CLI 面**：`keel run --session`、`keel sessions list|show`、`keel run --compact` 的参数与退出码；`--session` 与既有 `--profile` / `--manifest` 的组合规则；CLI 冒烟纳入门禁的范围（→ 04 稿）

## 7. 依赖与风险

- 依赖：Phase 1~4 全部内核能力（账本、一致点、恢复器、Cell、预算、网关、表面投影、Profile 装配、model/engine 两个 kind）；[research/01](../research/01-dsh-data-flow-survey.md) §4 作压缩与会话的设计输入
- **风险 1：复合键侵入面大**。跨 run 定址一旦渗进 `DECISION.basedOn` 等既有字段，会牵动 ADR-0008 与全部归因测试。缓解：只在新面（会话流、压缩区间）用复合键，既有字段口径不动；设计稿把边界写成"允许/禁止"清单
- **风险 2：并发会话写坏顺序**。两个进程同时 `--session` 会让"会话内单调"失真。缓解：单活租约（跨进程）+ 拒绝零写入 + 真进程用例（E6）
- **风险 3：摘要变成"新事实"**。模型生成的小结可能编造，一旦进入归因链就不可审计。缓解：摘要只进模型视图、永不进治理；原始事件永留；E3 的还原模式与"治理事件不进摘要输入"都要机械断言
- **风险 4：压缩打断 KV cache 前缀**，成本上升。缓解：bench 只观测记录；触发阈值保守；是否值得自动压缩留 backlog（本阶段手动 + 阈值）
- **风险 5：全量读取的性能与体积**。会话越长，投影成本越高。缓解：分页 + 类型过滤 + 从最近 run 反向取到足够量；基准段可见
- **风险 6：范围蔓延**（fork/回滚、UI、多 Agent 的诱惑）。缓解：不做清单 + backlog 通道；验收表不锚 UI 与业务场景
- **风险 7：恢复语义被误当"回滚"**。恢复是"补偿未决副作用后向前接续"，不是把世界还原到某个时刻。缓解：02 稿写清语义边界，E2 断言"补偿可回放且未决零悬空"
- 估时：不预设数字；四片均为纵向切片，量级参照 Phase 3/4 各切片

## 8. 关键决策点（待所有者确认后定稿）

- **K1 范围**：本阶段 = 会话流 + 跨 run 投影 + 续跑/恢复 + 会话预算连续性 + 压缩首版（手动 + 阈值触发）；fork/回滚、留存删除、自动压缩调度、UI、多 Agent、会话导出全部不做
- **K2 会话序列的定址**（本阶段最大结构决策）：a) **复合键** `(runId, seq)`——信封与既有归因字段一字不改，会话流只是"有序拼接 + 复合游标"；b) **会话级扁平 seq**——读写都更像单一日志，但要改"单写者 = 调度器、run 内单调"的既有事实（ADR-0004），写权与迁移面都变大。**设计稿须两案对比后给建议，所有者拍板**（第二道闸）
- **K3 顺序与单活**：run 序号由宿主在会话内分配并落账本（`RUN_STARTED` 载荷的追加字段，不新增事件类型）；同一会话同时只允许一个 run，跨进程用租约文件；拒绝路径复用既有 reasonCode（错误码零新增为默认口径）
- **K4 压缩的形状与触发**：a) 复用预留的 `surfaceOp`（挂在一条表面事件上，不新增类型）；b) 新增一条表面事件（语义直白、可审计，但要扩白名单与 ADR）。**设计稿两案对比后给建议，所有者拍板**（第二道闸）。首版触发 = 手动 `keel run --compact` + 阈值（阈值取账本里最近一次 `MODEL_USAGE` 的输入桶总量，确定性、不引入分词器依赖）
- **K5 续跑与恢复的统一口径**：前一个 run 有终态 = 续跑（不需要补偿，历史来自投影）；无终态 = 恢复（先补偿闭环、再挂快照、再新 run 接续）；两路共用"新 run + 会话历史 + 会话序号"，`keel recover` 的既有形状保留向后兼容
- **K6 红线与机械约束**：摘要生成必须走既有模型 seam（不得旁路 HTTP；`MODEL_*` 事件必须成对）；会话读取不得跨 `agentId`；投影仍为纯函数、不写账本；压缩只加视图操作事件，原始事件永不改删；密钥红线不变（D4 口径延续）

**确认记录**（2026-11-04，所有者）：K1~K6 全部按上文口径通过，本合同转定稿。其中两处保留"设计稿给出建议、所有者拍板"的第二道闸，同日已过闸：

- **K2-1**：选 **A 复合键**（`(runId, seq)` + 会话内 `sessionRun` 排序；信封与既有归因口径不动）→ [ADR-0025](../adr/ADR-0025-session-stream-addressing.md) 定稿。
- **K4-1**：选 **新增表面事件 `SURFACE_COMPACTED`**（白名单三类 → 四类；`surfaceOp` 保持预留给 `redact`）→ [ADR-0026](../adr/ADR-0026-compaction-as-view.md) 定稿。

二者落地口径见 [01 稿](../design/phase-5/01-session-stream.md) / [03 稿](../design/phase-5/03-compaction.md)；切片②起按此实现。
