# 旧生态反面教材：Phase 3 新插件评审的否决清单

- 状态：**生效**（2026-11-03 随 [ADR-0014](../../adr/ADR-0014-drop-legacy-ecosystem-compat.md) 建立）
- 来源：三枚真实第三方 DSH/Cordis 插件的第一批观察（[design/phase-2/08 §4/§5](../phase-2/08-real-sample-observation.md)）——**这些都是真实发布物里存在的写法，不是我们臆造的最坏情况**
- 用法：Phase 3 评审任何新插件（包括我们自己写的标杆插件）时逐条过；命中任一条即**不可转正**，除非先改插件。**不提供"以后再兼容"的通道**——旧生态的"能做到"从此是拒绝理由的清单，不是兼容待办

## 0. 先记住三条判据

Phase 2 用它们判旧插件，Phase 3 用它们判新插件，一字不改：

1. **控制不可旁路（I1）**：调度、授权、预算、恢复、账本由内核掌握，插件不能替换；
2. **副作用不可无痕（I4）**：越界副作用必须声明补偿语义，默认拒绝；
3. **上下文不可全局污染（I5）**：工具可见性、记忆、上下文按 Agent/Session 分区。

插件只负责"一件事做得好"——**能力**，不是**控制权**。

## 1. 控制权类（命中即否决，对应 I1 / 不变量 V6）

| #   | 旧写法（真实出处）                                                 | 为什么在 Keel 里不可接受                                            | 评审新插件时这么问                                                                                                             |
| --- | ------------------------------------------------------------------ | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| A1  | `ctx.systemPrompt.section(...)` 往系统提示里塞文案（2/3 样本）     | 决策输入由内核组装；插件改提示词 = 间接改写模型行为，归因链断在这里 | "你的行为是否依赖模型看到某段没人批准过的文字？" 正解：把提示词作为**声明的** `promptSections` 进 manifest，装配期可见、可审计 |
| A2  | `exec.concludeTurn()` 让工具宣告"本轮结束"（框架一手来源确认存在） | 直接接管 Agent Loop（V6）；"谁结束了这一轮"从内核手里被拿走         | "工具能不能决定何时停止？" 正解：不能；要影响走向只能走策略 hook 四个白名单点                                                  |
| A3  | 插件内自算预算/停止条件（Phase 2 #7，D 档）                        | 预算器与调度器是内核的                                              | "这个数字由谁记账？" 正解：读 `DECISION`/`ledger.read`，或走策略 hook                                                          |
| A4  | `exec.deferContext(msg)` 把新指令塞回下一轮（框架一手来源）        | 同上：控制流被工具改写                                              | "结果里能夹带下一条指令吗？" 正解：结果只描述事实，下一步由调度器决定                                                          |

## 2. 权限与能力类（对应 I4 与"内核拥有的量不接受临场指定"）

| #   | 旧写法（真实出处）                                                                                     | 为什么不可接受                                                        | 评审时这么问                                                                                       |
| --- | ------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| B1  | 运行中申请提权：模型参数给 `sandbox_permissions="danger-full-access"` + 插件调 `approvalSvc.request()` | **申请方 = 被授权方**，且权限由模型参数驱动；与"没声明即不存在"正相反 | "权限在什么时候确定？" 正解：装配期由 manifest 声明 + 授权器裁决；运行中只读不升                   |
| B2  | 用 `exec.agent` / 模型参数里的 `sessionId` 做跨会话操作                                                | 换身份 = 换授权主体；模型可伪造 sessionId 是更糟的一条                | "凭什么相信这个 id？" 正解：身份由通道盖章，插件不持有；跨域用 scope                               |
| B3  | `ctx.get('shell')` / `ctx.get('web')` 自取宿主服务（抓取类样本的主力路径）                             | 服务定位 = 绕过授权与留痕；调用面不在账本里                           | "你碰到的每一样东西，有没有对应的 manifest 能力？" 正解：声明 `net.fetch`/`fs.*` 词表 + allow 清单 |
| B4  | 按 npm 名 import 宿主包（`@deepseek-ai/*`），`peerDependencies` 指向框架                               | 供应链与版本耦合进插件；装载失败还看不见                              | "除运行时外，你依赖哪些包？" 正解：零运行时三方依赖（Keel 的底线），需要的宿主面走 manifest        |
| B5  | 工具定义里自带 `timeoutMs` / `isConcurrencySafe` 却不进声明                                            | 内核可调度的量由插件单方面决定 = 静默改判                             | "超时与并发由谁定？" 正解：进 manifest `resources`，运行期不可改                                   |

## 3. 状态与协作类（对应 I5 / 故障不可级联）

| #   | 旧写法（真实出处）                                                                     | 为什么不可接受                                        | 评审时这么问                                                                       |
| --- | -------------------------------------------------------------------------------------- | ----------------------------------------------------- | ---------------------------------------------------------------------------------- |
| C1  | `ctx.provide(id, impl)` 发布扩展点、别的插件 `ctx.inject([id])` 取用（识图分析器样本） | 跨插件写通道 + 隐式依赖顺序；谁在用谁、谁先起全凭约定 | "A 插件怎么把东西交给 B？" 正解：**经工具调用参数**（授权 + 留痕），或各自独立工作 |
| C2  | `ctx.bus.emit/on` 事件总线（Phase 2 #15）                                              | 同上，且故障与上下文会顺着总线级联                    | 同上                                                                               |
| C3  | `ctx.share` / `ctx.state` 共享可变状态（Phase 2 #8）                                   | 谁产生状态谁持有；共享可变状态让回滚与归因同时失效    | "这份状态的 owner 是谁？" 正解：只在产生它的 Cell 内；要给别人看就走账本只读       |
| C4  | 外部组合层 `cordis.patch.yml` 决定装不装、传什么 config（3/3 样本都有）                | 行为定义在插件之外、观察不到、审计不到                | "插件装上是什么行为，看哪个文件就知道？" 正解：manifest 是唯一事实源               |

## 4. 形态与工程类（不否决能力，但否决"不可评审"）

| #   | 旧现象                                                                   | 后果                                                             | Phase 3 的硬要求                                                             |
| --- | ------------------------------------------------------------------------ | ---------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| D1  | 入口形状随框架世代变（`activate` → `apply(ctx, config)`）                | 我们按上一世代建的表一年就过时（ADR-0014 的直接理由）            | 插件入口 = Keel 自己的形状（Cell 入口 + `export const tools`），不跟外部框架 |
| D2  | 工具定义字段名各代不同（`handler` → `execute`，`schema` → `parameters`） | 字段读错会注册出"有名字、无 schema、无处理器"的空工具 = 静默降级 | 缺字段**必须拒**（五步校验里加一条），不允许默认值兜底                       |
| D3  | 浏览器半 `dsh.client.platform="web"`，功能主体在另一个进程               | 一半功能在 Keel 视野之外，却挂在同一个包名下                     | 一个包只承载 Cell 形状的能力；前端属于宿主，不属于插件                       |
| D4  | 观察工具给自己打高分（`ACCEPT` + 退出码 0，实际零工具）                  | 机器口径假阳性（08 稿 D2/D3）                                    | Phase 3 的脚手架必须把"装载成功 / 观察到面 / 校验通过"分开报                 |
| D5  | 关键行为来自外部 config 或原生 IO，观察不到                              | 候选声明天然偏低，审核无从下手                                   | 缺项清单必须显式列"不可观察面"，人工补声明并留痕                             |

## 5. 评审流程（建议，随 Phase 3 合同定稿后写进 standards/05）

1. **读 manifest**：能力、资源、补偿三项是否自洽，有没有"运行时才决定"的量；
2. **过本清单**：A/B/C/D 四组逐条，命中即退回（不写"以后再说"）；
3. **看代码的三件事**：入口形状、工具体字段、import 清单（零三方依赖 + 无宿主包名）；
4. **跑门禁**：五步校验 + 本仓六道门禁 + 一条真进程用例；
5. **留痕**：转正记录写"依据了哪几条反面教材不适用"（不是"审过了"）。

> 一句话：**旧生态教给我们的不是"怎么兼容"，而是"什么必须拒绝"。**本清单是那份学费的收据。
