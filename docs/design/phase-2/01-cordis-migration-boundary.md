## 1. 这份文档回答什么

一句话问题：**一个按旧框架（Cordis）写的存量插件，搬到 Keel 上还能不能跑？跑到什么程度？哪一段代码必须改？哪一段永远不许再这么写？**

判据（三条，缺一即文档不合格）：

1. 旧写法每一种都有归属——要么映射到 Keel 的受控等价物，要么**显式拒绝**；
2. 拒绝必须有替代写法（"改成什么"），不能只说"不支持"；
3. **禁止静默降级**——映射不到的部分绝不"先凑合跑起来"，那是把旧框架的病灶以新框架的名义重新制造出来。

> 为什么不追求"全量原样兼容"：旧框架的四个病灶（全局注册表污染、崩溃级联、控制流被插件接管、副作用无回收）恰恰是靠这些写法实现的。原样兼容 = 原样保留病灶。架构总览 §7 与 ADR-0001 的立场是"承接生态，不承接控制权"。

## 2. 承接档位定义

| 档               | 含义                                 | 对存量插件方的要求                        |
| ---------------- | ------------------------------------ | ----------------------------------------- |
| **A 直接可用**   | 适配层自动映射，代码一行不改         | 无（但行为差异需知晓，见 §3"语义变化"列） |
| **B 加声明即可** | 代码不改，但要补一张 manifest 报关单 | 按新格式补权限/资源/补偿/兼容声明         |
| **C 必须改写**   | 旧写法没有安全等价物，需要改代码     | 按"迁移改法"列重写那一小段                |
| **D 不再允许**   | 与内核不变量直接冲突，永远拒绝       | 这段能力由内核提供，插件不再自己实现      |

## 3. 边界表（核心交付）

## 4. 存量插件方需要做什么（汇总）

- **一行不改**：#1 #2 #3 #10 #13（但要理解：可见性按会话隔离、崩溃成为可见事件、主进程不再被拖住；两处例外已在表内注记——#1 的"同步消费注册返回值"属 C 档一行 `await`，#2 的"启动期塞钩子"一支归 #14 的 D 档通道）
- **补一张报关单**：#4 #5 #11 #12（权限/资源/账本/依赖声明）
- **改一小段代码**：#6（模型调用改走网关）、#8（拆共享可变状态）、#9（副作用改为声明式补偿）、#15（跨插件事件总线改走工具参数或只读账本）
- **彻底放弃**：#7（自建控制流与预算）、#14（用策略插件绕控制面）

## 5. 材料性质与回填义务（已定，不可绕过）

本表的**档别判定**目前来自设计简报与架构篇对旧框架的描述，尚未对着真实存量插件代码逐条核过。所有者已定的处置：**合成组打底，真样本到位后补跑**。

1. **验收材料**：先按旧框架典型写法亲手写出 A/B/C/D 四档代表样本（Phase 2 合同 §2），并**刻意包含真实世界的野路子探针**——动态 require、原型链猴子补丁、进程级全局 hack、加载顺序依赖。真实存量插件（DSH/Cordis 生态源码或安装副本）一旦到位，B1 与 B5 同场景复跑一次。**证据表述纪律**：合成组只能表述为"我们设想的写法已验证"，不得表述为"真实存量插件已验证"；两批材料性质在 Phase 2 报告分开列。
2. **每接一个真实插件都要回填本表**：出现新符号（旧 API 里本表没覆盖的调用面）→ 归入某档并补一行；Phase 2 收官时核对"表中 D 档是否被任何实现悄悄支持了"——**静默降级即验收失败**（B4/B5 一票否决）。
3. **D 档零例外**（所有者确认 2026-11-02）：#7 与 #14 不因"存量插件普遍这么写"而开口子。承接方式只有一条路：迁移手册给出等价出路（四个白名单 hook + 内核预算/调度能力），让"这么写也能达到目的"成立。
