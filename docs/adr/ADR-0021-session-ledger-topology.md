# ADR-0021：run 内会话与账本的拓扑（统一流 + 表面投影 vs 双日志）

- 状态：**定稿**（2026-11-04 所有者拍板：选 A 统一流；[phase-4 合同](../roadmap/phase-4-profile-engine-loop.md) §8 K3 的两案对比已完成，第二道闸通过）
- 日期：2026-11-04
- 关联：[phase-4 合同](../roadmap/phase-4-profile-engine-loop.md) §6 C1/C2/C4；[research/01](../research/01-dsh-data-flow-survey.md) §2.1/§2.3/§4（DSH 单一日志 + 表面投影的实况）；[ADR-0004](ADR-0004-ledger-consistency-point.md)（轮边界一致点）；[ADR-0008](ADR-0008-decision-attribution-upper-bound.md)（`basedOn` + `throughSeq`）；[ADR-0013](ADR-0013-model-stream-pull-chunking.md)（拉式分片与流终结算）；[契约 §5](../design/phase-1/01-core-api-contract.md)（事件表）；[ADR-0017](ADR-0017-runtime-context-layering.md)（`ToolCatalog` + `PageStore`）
- 取代：无

## 背景

Phase 4 要让 engine（Cell 进程里的 ReAct 循环）在每一步向模型提交"到目前为止的对话与工具结果"。今天 Keel 没有任何"模型可见上下文"的概念：账本记的是治理事实（授权、预算、裁决、工具调用与结果、效果），模型调用的正文（提示与回答）不落账本；`PageStore` 只有换页原语，没有"会话表面"。

于是 C1 要回答的第一个问题是**模型视图从哪来**。合同把候选收敛为两案：a) 统一流——账本即唯一事实，模型视图是账本的表面投影；b) 双日志——账本记治理与归因，另开一份会话日志记载荷，跨日志用 seq 引用。

这不是命名之争，而是**崩溃一致性、重放、写权、体积**四件事同时选边，且 engine 的上下文装配写法被它直接压住（合同 §7 风险 1）。

## 事实核对（现状，带证据）

- **F1 账本形状**：信封 = `{seq, ts, runId, sessionId, agentId, type, schemaVersion, payload}`，无哈希链（`packages/core/src/events.ts:64-74`）；`seq` 在执行期分配、文件内单调（`packages/core/src/ledger.ts:124-145`）；追加只写页缓存**不 fsync**，`checkpoint()` 才 `sync → 写 CHECKPOINT → sync`，段满 8MB 滚动（`ledger.ts:156-175`，`DEFAULT_SEG_MAX_BYTES` 28 行）；完成性靠「单调 seq + CHECKPOINT + 尾部撕裂即停」（`ledger.ts:204-216`），不靠链式哈希。
- **F2 事件词表封闭、26 类**（`events.ts:17-44`），其中模型侧只有 `MODEL_INVOKED`（模型/请求摘要）与 `MODEL_USAGE`（用量/费用/`truncated`）——**没有承载模型正文的事件**。`TOOL_INVOKE`/`TOOL_RESULT` 已在账本里，含结果状态与摘要（契约 §5）。
- **F3 归因已有上界锚**：`DECISION.basedOn` 显式引用 + 账本盖章 `throughSeq`（ADR-0008；`events.ts:118-134`、`ledger.ts:38-45,148-154`）。归因**只认账本 seq**，任何第二份日志都必须靠引用与之缝合。
- **F4 Cell 不能直写账本**：Cell→Host 只有 `ledger.read`（强制收窄到调用方 runId，`packages/host/src/cell-server.ts:60-121`）；scope/subject 由宿主绑定、舱内不自报（同文件 33-41）。表面事件的写入权因此天然在 Core 侧。
- **F5 上下文设施是"页"，不是"会话"**：`PageStore` 提供 `pageOut/pageIn/pageVersion`（`packages/core/src/page-store.ts:18-70`），`CONTEXT_PAGED` 事件已定义、由调用方决定写入；`ToolCatalog` 管工具可见面（`packages/core/src/tool-catalog.ts:29-92`）。
- **F6 跨 run 能力为零**：无会话持久化、无 fork/resume、无压缩；run 结束即收束（合同 §2 不做清单）。
- **F7 DSH 的参照**：单一 append-only 日志 + 14 类核心事件 + 插件声明合并；模型视图 100% 日志表面投影（`deriveMessages` 全量投影）；压缩是 `surfaceOp` 视图操作，原始事件永留（research/01 §2.1、§2.3、§4）。它的痛点是"日志体积与写放大"由 checkpoint 批量 + 有界合并吸收。

## 方案 A：统一流（账本 + 表面事件族 + 纯投影）

1. 账本仍是 run 的唯一事实。新增**表面事件族**（白名单、封闭）：承载模型可见消息（用户轮、模型回答、工具结果进表面的视图、系统提示），与既有治理事件同一条 seq 序列。
2. 模型视图 = **纯函数投影** `project(events[0..n])`：只吃表面事件、只按白名单，输出消息数组 + 本步工具集；结果可丢、可重算，不另存。
3. 治理事件（授权/预算/裁决/效果/检查点）**永不进模型视图**，但全留在账本供审计与归因。
4. 表面事件可带 `surfaceOp`（本阶段**预留不实现**，只定形状），压缩将来是视图操作。

## 方案 B：双日志

1. 账本保持今天的样子（治理事实与归因），体积不因模型正文增长。
2. 另开 per-run 会话日志：消息载荷、自己的 seq；账本事件引用会话 seq（或反之）。
3. 模型视图 = 会话日志的 fold；重放 = 两日志按引用 join。

## 对比

| 维度                | A 统一流                                                   | B 双日志                                                |
| ------------------- | ---------------------------------------------------------- | ------------------------------------------------------- |
| 唯一事实来源        | 一条日志，审计/重放/归因同一把尺                           | 两条日志，谁是权威需逐字段裁定                          |
| 崩溃一致性          | 沿用 ADR-0004：轮边界一个 fsync 点，尾部撕裂即停           | 需两套撕裂修复 + 跨日志缝合窗口（一条落、一条未落）     |
| 归因（V6/I1）       | `basedOn`/`throughSeq` 直接覆盖表面事件                    | 归因跨日志跳转，"这条消息基于哪些治理事实"要二次 join   |
| 重放                | 同序列重放，投影可重算                                     | 依赖两日志相对完整，缺一不可重放                        |
| 写权                | 结构上只有 Core 可写（F4 已成立）                          | 新日志需要自己的写权/授权面，等于第二条治理链           |
| 账本体积            | 增长（模型正文进账本）；由段滚动与 checkpoint 频率吸收     | 账本轻，但会话日志同样要落盘与修复                      |
| fsync 压力          | 不增点（仍按轮）；若上 dispatch 屏障则每模型调用一次（C3） | 不增点，但两个文件各一个同步点                          |
| 压缩/裁剪           | 视图操作，原始事件不动（照 DSH）                           | 会话日志可独立裁剪，账本不受影响（真实好处）            |
| 本阶段代价          | 新增表面事件族 + 投影函数 + 白名单校验                     | 新增日志、存储、读通道 op、跨日志一致性协议、第二套恢复 |
| 后续 UI/跨 run 扩展 | 投影与白名单形状可复用（research/01 §5 四件套）            | 前端要同时理解两条日志                                  |

## 建议

**选 A（统一流）**，理由按权重：

1. **不变量优先**：I3"状态不可丢失"与 I1"控制不可旁路"在 A 下是同一份账本的直接推论；B 引入第二条写链，等于把"唯一事实"降级成约定。
2. **代价已被现存机制吸收**：Keel 的 fsync 频率本来就按轮（ADR-0004），A 增加的是字节而不是同步点；8MB 段滚动与灾备读取已经就位（F1）。
3. **B 的真实收益只有一个**（载荷可独立裁剪/留存），而它属于"压缩与留存策略"，本阶段明确不做（合同 §2 不做清单）；为一个不做的事先付一致性成本不划算。
4. **演进方向一致**：后续 ui/桌面阶段要的是"白名单 + 整值投影"，正是 A 的形状（research/01 §5）；B 会迫使前端理解两套序。

B 不是坏设计，它的成立条件很具体：**账本体积被实测证明不可接受，或载荷留存策略必须与审计账本分离**（合规/脱敏）。触发其一再重评，届时投影函数可复用、迁移面有限。

## 决策（2026-11-04 所有者拍板：选 A；以下逐条转定稿）

1. **唯一事实 = 账本**（run 范围）：表面事件与治理事件共用一个 `seq` 序列、一个 `checkpoint`、一套撕裂修复。
2. **模型视图 = 纯函数投影**：输入账本事件流，输出消息数组；不落独立存储，缓存可丢、可重算；投影带版本号，重算结果与版本绑定。
3. **表面事件族 = 封闭白名单**：只有被列入白名单的类型可进模型视图；首版词汇表在契约修订中定稿（C2），本 ADR 只定"白名单 + 纯投影"的结构。治理事件不因"看起来有用"而进入白名单（改白名单走 ADR）。
4. **`surfaceOp` 只允许出现在表面事件上，本阶段不实现**；字段形状在契约修订中预留（C4），非法组合在校验层拒绝（借 DSH 的"插件记录强制 ignorable"教训，research/01 §4）。
5. **写权结构不变**：Cell 无直写账本通道（F4 现状），engine 请求表面写入必须经 Core 通道；Surface 投影不提供写入接口。
6. **跨 run 不改变本拓扑**：`sessionId` 已在信封里（F1），跨 run 会话 = 后续阶段在"同一 session 的 run 序列"上做投影，届时追加修订 ADR，不推翻本条。
7. **体积与持久化沿用 ADR-0004**：不逐事件 fsync；是否在模型 dispatch 前加屏障（C3）由契约/账本设计稿给出建议，本 ADR 只声明"不新增同步机制，只可能复用 checkpoint"。

## 后果

- 积极：重放、归因、审计、模型视图共用一条时间线；模型正文与 tool 结果同源，不会出现"账本有结果、会话日志没有"的分裂；UI 阶段的投影/白名单可直接复用。
- 代价 / 风险：① 账本字节增长（模型正文），需要基准段观测（合同 §4 基准）；② 投影是热路径，必须纯且可被测试钉死（快照式投影测试）；③ 白名单是新的评审面，误加一条 = 治理事件泄漏进模型提示。
- 重评条件：基准显示账本 IO 成为瓶颈（触发 ADR-0004 有界合并重评）；或出现"载荷必须与审计账本分离留存"的合规要求 → 转 B，投影函数保留。
- **被否方案**：B 双日志（理由见上，非永久否决，重评条件已写）；C "模型正文不落账、上下文只活在内存"——崩溃后不可重放、D5 归因不成立，直接违反 I3；D "照抄 DSH 并立即实现压缩"——合同 §2 已排除压缩，属范围蔓延。

## 确认记录（2026-11-04）

- **K3-1**：选 **A 统一流**（建议案通过）。
- **K3-2**：接受"表面事件族"作为契约新概念（新事件类型 + 封闭白名单 + 纯投影函数），不把模型正文塞进现有 `MODEL_*` 事件。
