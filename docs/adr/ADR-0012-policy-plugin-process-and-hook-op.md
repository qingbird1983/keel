# ADR-0012：策略插件的执行位置与插话通道（独立进程 + `policy.hook` op）

- 状态：定稿（2026-11-03 所有者授权，见切片④设计稿 [phase-2/06](../design/phase-2/06-policy-chain-and-d-tier-refusal.md) §7 三项确认）
- 日期：2026-11-03
- 关联：切片④设计稿 §2 事实核对（F1/F4/F5/F6/F7/F11）与 §3.1；契约 [§3.3 可见面矩阵 / §4.8 策略扩展点 / §5 事件表 / §7 超时表](../design/phase-1/01-core-api-contract.md)；[ADR-0005](ADR-0005-cell-isolation.md)（进程级隔离）；[ADR-0011](ADR-0011-cell-load-gate.md)（装载门与就绪凭据）；[Phase 1 报告](../design/phase-1/report.md) §3 第 3 条（本 ADR 兑现的回填项）
- 取代：无——本篇**新增一个宿主→舱 op 并规定策略插件的进程位置**；四 hook 的语义、默认策略、禁区校验与既有事件（`HOOK_CALLED`/`HOOK_VERDICT`）全部不动

## 背景

契约 §4.8 的四个 hook 早就实现完了：调度器在四个点位调用总线、总线写两条账本事件、裁决 seqs 进 `DECISION.basedOn`、超时与违规一律回落默认策略。但**总线在生产路径上是空的**——`HookBus.register` 的调用者只有测试，`apps/keel` 造了总线之后无人注册，报关单里的 `hooks` 字段也没有任何运行期消费者（`assembler.ts` 只是 `m.hooks ?? []` 收下来）。于是"策略插件只能插话、不能接管"这条主张从来没有真进程凭据，而验收 B4 的"D 档拒绝且零部分生效"也只活在 in-process 单测里。

补这段链要先回答一件架构上没写死的事：**策略插件的代码跑在哪里**。契约 §3.3 对策略插件那一行写得很硬——可见 = "四个 hook 被调用（被动），无主动接口"，不可见 = "除 hook 入参外的一切"。这句话直接否决了"在宿主进程里 import 策略模块"：一个模块只要能被 import，就能读到宿主内存与内核命名空间（Ledger、Scheduler 都在同一个模块缓存里），§3.3 在接通当天就成谎话；而且策略模块里的一次忙等或一次抛错会带走宿主（违 I2）。另一头，全宿主共享一个策略进程虽然省进程数，但它不属于任何 run：崩溃时既不能 abort 也无从归因，一次故障波及全部在途运行——正是 I2 要防的形态。

## 决策

1. **策略插件跑在自己的进程里**（"策略舱"）：复用 ADR-0005 的进程级后端与 ADR-0011 的装载门。入口只认一种导出 `export const hooks = { <hookName>: fn }`，**不注入 `CellClient`、不注入任何主动接口**；`hooks` 的键集必须 ⊆ 报关单 `hooks` ⊆ 四 hook 白名单，越界项在装配期整份拒绝（不是忽略）。
2. **新增一个宿主→舱 op `policy.hook`**：载荷 `{hook, round, input}`，应答 = verdict 原样。**裁决与禁区校验留在内核的 HookBus**——把校验挪进舱内等于让被审者自审；舱只负责"给出响应"。入参由调度器既有构造提供（轮号、工具名与参数、模型与试次、错误摘要、耗尽层级与预算视图），不含任何可操作句柄。
3. **失败语义完全沿用既有 fallback**：超时 / handler 抛错 / 响应违规 / 通道断 → 采用 §4.8 的默认策略并落 `HOOK_VERDICT{fallback:true}`。**不新增错误码**（与 ADR-0011 同一姿态：§6 是封闭表，这里没有新语义要表达）。策略时限只用契约 §7 的 hook 超时（200ms），不引入第二套时限数——策略报关单的 `resources` 按 schema 必须是空对象，本来就没有"工具时限"这个量。
4. **策略舱不属于任何 run**：它不调 `attachRun`，因此其进程退出不触发任何 run 的 abort（`onCellExit` 的 `if (ref)` 分支天然跳过）。这条要有测试，不靠"看起来不会"。
5. **同一插话点被两份策略声明 → 装配期整份拒绝**：不注册、不产候选、给明确错误。`HookBus.register` 的"同名覆盖"从此只允许装配器在**已查重**的策略集合上调用——覆盖就是静默改判（后一份策略悄悄吃掉前一份的否决权，账本里只看得到"有人说话"，看不出说的是谁）。
6. **装配审计扩展**：`ASSEMBLY_RECORDED` 增 `policies: [{name, version, hooks[]}]`（**追加字段**，Phase 1 的旧账本样例仍可读）。理由：策略一次话都没插时账本对它零记录，"绑了但没说话"与"根本没绑"否则不可分辨，而 V6 的归因主张要能回答"这一轮究竟是谁的话"。

## 被否方案

| 方案                             | 否掉的理由                                                                                                                          |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 宿主进程内动态 import 策略模块   | 违反 §3.3"除 hook 入参外的一切不可见"（模块可见宿主内存与内核命名空间）；策略侧一次忙等/抛错带走宿主 = 破 I2；B4 的硬拒绝从此有反例 |
| 全宿主共享一个策略进程           | 不属于任何 run，崩溃既不能 abort 也无从归因，一次故障波及全部在途运行；run 间共享进程踩 I2"无跨 Cell 共享可变接口"的边缘            |
| 后声明者覆盖 + 账本记被覆盖者    | 要新定义"谁优先"的语义并扩展事件载荷；且默认行为仍是覆盖——静默改判换了个名字而已                                                    |
| 校验/裁决逻辑下移到策略舱内      | 让被审者自审：§4.8 的响应禁区（V6）与默认策略必须由内核独占                                                                         |
| 不扩装配审计，只用 `HOOK_*` 反推 | 省一次契约注记，代价是"绑了却零介入"不可观测——正是 B4/B7① 评审要看的那一半                                                          |
| 给策略舱也上 `toolCallTimeoutMs` | 策略报关单的 `resources` 必须为空对象（schema 硬约束），插话时限的唯一来源是契约 §7 的 hook 200ms；再引入一套数就是两张皮           |

## 后果

- 积极：B7① 第一次有可跑形态——真实 run 里四个插话点的每次介入都可从账本归因；B4 的"D 档拒绝 + 零部分生效"从此能在真进程上复演；策略与能力在同一套进程隔离与装载门下，生命周期语义只有一张表；策略"绑了但没说话"变成可审计事实。
- 代价：每个绑定了策略的 run 多一个 OS 进程（冷启动量级见 ADR-0005），每次插话多一次跨进程往返（在 200ms 预算内，实测数量级为毫秒；开销由 B8 基准观察，不设阈值）；契约需补两处实现期注记（§4.8 执行位置与 op、§5 `ASSEMBLY_RECORDED.policies`）；本 ADR 是本阶段第一处**新增帧 op**，后续任何策略方向的扩展都要在此口径上继续论证。
- 重评条件：① 多策略并存需要"链式/优先级"语义时（本片只做到"冲突即拒"）；② 策略热更新要复用切片② 的升级接缝时（策略舱有版本但没有迁移钩语义——策略应无状态，若有状态说明设计漂了）；③ 容器/microVM 后端启用后冷启动与进程数代价变化（ADR-0002/0005）；④ 观测插件（§3.3 另一行，同样"被动"）接入时若需要第三种通道形状，应回头比较本篇的取舍是否仍成立。

## 实施注记（2026-11-03 施工期追加；只补事实，不改上面任何一条决策）

1. **决策 2 的帧载荷落地为 `{hook, input}`，没有 `round`**。原因不是省事：内核 `HookBus` 递给 handler 的参数只有入参本体（`hooks.ts` 的 `handler(input)`），轮号在同一次调用里由内核写进 `HOOK_CALLED{hook, round}`。要把轮号塞进帧，就得改内核 handler 签名——那动的是被审者看不到、内核独占的那一侧，不在本篇授权范围内。**归因链因此仍然完整**：账本里每条 `HOOK_CALLED` 都带轮号，策略舱拿不到的本来就不该是它的输入。
2. **决策 5 的"整份拒绝"在实现里加了一条次序约束**：`bus.register` 是装配的**最后一步**——先把所有策略舱起好并探到就绪，再整批注册。半途失败若只收进程不收注册，总线上会留下指向已 reaped 舱的 handler（`HookBus` 没有也不该有 `unregister`：注册是装配期动作），下一次同总线的 run 会在它上面拿到一条 `fallback:true`——那是"看起来拒绝了但悄悄降级"。测试面：`packages/host/test/policy-link.test.ts` 的"第二份策略起不来 → 已经起来的舱一并收干净，且一份 handler 都没留下"。
3. **决策 3 在实施里的形态是一句话**：就绪探测未得到应答时报 `TRANSPORT/TIMEOUT` 或 `TRANSPORT/BADFRAME`（策略进程在装载期就退出时，通道先断 = 后者），归因位在 `detail.reason = "CELL_NOT_READY"`。真进程样本里两种码都会出现（`tests/policy-chain-attribution.test.ts` 的装载拒绝那条按这个集合断言），所以"不新增错误码"不是一句口号，而是封闭集合内的两个既有码各对应一种真实时序。
4. **决策 3 的时限在实现里只有一个来源**：`HOOK_TIMEOUT_MS`（契约 §7 的 200ms）由 `@keel/core` 导出，宿主→策略舱的请求超时直接用它——不在宿主再写一个 200，否则两处失败走的是两套数。
