# ADR-0025：会话序列的定址（复合键 vs 会话级扁平 seq）

- 状态：**定稿**（2026-11-04 起草并定稿：两案对比后，所有者第二道闸拍板选 **A 复合键**；落地见 [01 稿](../design/phase-5/01-session-stream.md)）
- 日期：2026-11-04
- 关联：[phase-5 合同](../roadmap/phase-5-session-continuity.md) §6 S1/S2/S3；[ADR-0021](ADR-0021-session-ledger-topology.md) 决策 6（跨 run 会话 = 同一 session 的 run 序列上做投影）；[ADR-0004](ADR-0004-ledger-consistency-point.md)（run 内单写者、轮边界一致点）；[ADR-0008](ADR-0008-decision-attribution-upper-bound.md)（`basedOn` / `throughSeq` 的 run 内口径）；[research/01](../research/01-dsh-data-flow-survey.md) §4（DSH 的单一 `log.length` 会话编号）；[设计稿 01](../design/phase-5/01-session-stream.md)
- 取代：无

## 背景

Phase 4 结束时，"会话"只是信封里的 `sessionId`：账本按 `<agent>/<session>/<run>` 分目录，`seq` 在 run 内单调，跨 run 读取面为零。Phase 5 要让同一会话的多次 run 共用一条可重算的模型视图，第一个问题就是**事件怎么定地址**——这决定游标、压缩区间、读取 API 和"同一账本两次重算是否一致"。

两个候选：A 复合键（运行序 + run 内 seq），B 会话级扁平 seq（整个会话一条连续编号）。

## 事实核对（现状，带证据）

- **F1 run 内单写者、seq 执行期分配**：`seq = lastSeq+1` 由写队列分配（`packages/core/src/ledger.ts:139-140,333-346`）；已有账本的 run 拒绝第二个写者（同文件 :279-286）。
- **F2 跨 run 读取不存在**：`ledger.read` 过滤键必填 `runId`，注释明确"跨 Run 全量读取暂不开放"（同文件 :11,47-52）；跨 run 只能扫目录。
- **F3 归因字段是 run 内整数**：`DECISION.basedOn` 与 `throughSeq` 都是"本 run 的 seq"（ADR-0008；`packages/core/src/events.ts:161-166`）。
- **F4 run 目录名无序**：`run-<randomUUID 前 8 位>`（`apps/keel/src/cmd-run.ts:101`），目录扫描给不出先后。
- **F5 投影不看 runId**：`projectSurface(events)` 只吃事件数组（`packages/core/src/surface.ts:45-85`）——拼接顺序由调用方负责。
- **F6 DSH 的参照是单一日志**：会话即 append-only 日志，`seq = log.length` 连续（research/01 §4）；它的写权是开放的、靠三重门约束。

## 方案 A：复合键（运行序 + run 内 seq）

1. 会话 = `(agentId, sessionId)` 下按 `sessionRun`（会话内单调整数）排序的 run 序列；`sessionRun` 由宿主在会话租约内分配，落 `RUN_STARTED` 载荷（追加字段）。
2. **事件地址 = `(runId, seq)`**；会话游标 = `{run: sessionRun, seq}` 的不透明编码。信封、`seq` 语义、单写者模型全部不动。
3. 既有归因字段保持 run 内口径；跨 run 的引用只出现在新面（会话游标、压缩区间）。
4. 会话投影输入 = 按 `sessionRun` 升序拼接、每个 run 内按 `seq` 升序的事件流（事件自带地址）。
5. 历史账本（无 `sessionRun`）按 `RUN_STARTED.ts` 升序、`runId` 兜底排序，排在编号 run 之前；新 run 从 `max(已有)+1` 起编号（兼容规则写进契约）。

## 方案 B：会话级扁平 seq

1. 会话维护一个全局单调计数；每个 run 写入时从会话取号，事件信封的 `seq` 变成会话级。
2. 读取天然连续；游标是一个整数；压缩区间也只是一个整数区间。
3. 代价：**写权从"run 内单写者"扩散到"会话级分配器"**。要么每个 run 写入前向分配器取号（跨进程锁 + 网络/文件往返），要么改成本地批量预留（预留块之间的空洞与崩溃恢复要另立协议）。
4. 要么放弃 run 内 seq 语义，要么维护两套编号（run 内用于归因、会话级用于定址）——**两套编号并存时，B 的名字优势消失，问题回到 A**。

## 对比

| 维度         | A 复合键                                          | B 会话级扁平 seq                                    |
| ------------ | ------------------------------------------------- | --------------------------------------------------- |
| 写权与一致性 | 不增写者；沿用 run 内单写者 + 一致点（ADR-0004）  | 需要会话级分配器（跨进程锁/预留协议），一致性面扩大 |
| 兼容         | 信封、`seq`、`basedOn`/`throughSeq` 一字不改      | 改信封语义或引入双编号，旧账本与测试全要迁移        |
| 归因（V6）   | 仍然只认 run 内 seq，跨 run 引用只在新面显式标注  | 归因天然跨 run，但与既有验证过的口径冲突            |
| 压缩区间     | 区间是复合的 `{from:{runId,seq}, to:{runId,seq}}` | 区间是单个整数，最简洁                              |
| 读取         | 需按 run 序遍历（目录扫描 + `sessionRun`）        | 顺序天然，但读取仍要跨多个文件                      |
| 崩溃恢复     | 与既有恢复器一致（新 runId 延续）                 | 需要在恢复里维护会话计数器的连续性                  |
| 迁移面       | 新增读取面与游标，不动既有事实                    | 全库账本/测试/契约的编号口径迁移                    |
| 复杂度       | 地址多一层，但边界清楚                            | 表面简单，隐藏分配器与双编号                        |

## 建议

**选 A（复合键）**，理由按权重：

1. **不变量优先**：I1"控制不可旁路"与 ADR-0004 的"单写者 = 调度器"是现成的地基；B 为了读取方便去动写权，是把最贵的部分换最便宜的收益。
2. **归因口径已经验证**：`basedOn`/`throughSeq` 是 Phase 2 至今的归因锚（ADR-0008、`tests/decision-through-seq.test.ts`）；B 会牵动全部归因测试与审计口径。
3. **代价集中在读取层**：A 的复杂度可被一个读取 API + 不透明游标封住，调用方只看到 `nextCursor`；B 的复杂度在分配器与恢复协议里，藏不住。
4. **演进不堵路**：将来若真需要扁平编号（例如导出给外部工具），可以在读取层生成"会话视图序号"，不必改账本——A 的地址是事实，B 的编号是视图。

B 的成立条件很具体：**会话的跨进程写者不止一个，且读取性能被实测证明不可接受**。触发其一再重评；届时读取层可保留。

## 决策（2026-11-04 所有者拍板：选 A）

会话流 = 按 `sessionRun` 升序的 run 序列拼接，事件地址保持 `(runId, seq)`；`sessionRun` 落 `RUN_STARTED` 追加字段；旧账本按 `RUN_STARTED.ts` + `runId` 兜底排序并排在编号 run 之前；既有 `basedOn` / `throughSeq` 的 run 内口径不改。

- **K2-1**：选 **A 复合键**（建议案通过）。
- **K2-2**：复合地址只在新面使用（会话游标、压缩区间）；信封与既有归因字段不动。
- **K2-3**：单活与序号分配由宿主在会话租约内完成（01 稿 §3.1/§3.3），不改账本写路径。

## 后果

- 积极：账本事实面零迁移；会话游标、压缩区间与投影顺序都在新增的读取层定义；旧账本（无 `sessionRun`）有确定的兼容排序。
- 代价 / 风险：① 会话读取要按 run 序拼装，性能受 run 数量影响（分页 + 类型过滤缓解）；② 复合地址会让"跨 run 引用"看起来比整数麻烦，需要文档与类型名把边界写死（只在新面使用）。
- 重评条件：会话级写者出现多进程并发（需要统一分配），或读取基准显示拼接成本不可接受 → 重评 B，读取 API 形状可保留。
- **被否方案**：B（理由见上，非永久否决）；C "把会话当单个 run、永不跨 run"——等于不做本阶段，违反 I3 的长程语义。
