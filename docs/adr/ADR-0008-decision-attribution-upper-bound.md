# ADR-0008：决策依据改为"关键引用 + 上界游标"

- 状态：定稿
- 日期：2026-11-02
- 关联：[ADR-0004](ADR-0004-ledger-consistency-point.md)（账本与一致点）；契约 [§4.1 / §5](../design/phase-1/01-core-api-contract.md)；Phase 1 报告 §3 限制 2 / §10 回填清单；Phase 2 合同 [§2「做」](../roadmap/phase-2-cordis-compat.md)
- 取代：无——本篇扩写 DECISION 的归因面，不改 V6 立场（依据仍由内核记账，插件不可写）

## 背景

Phase 1 验收 A6（审计归因，一票否决）暴露一处语义缺口：`DECISION.basedOn` 只登记**调度器自己写入**的事件编号。账本并非只有单一写入者——授权器的 `AUTH_DENIED`、网关的预算事件、效果追踪器的 `EFFECT_*`、宿主的 `STATE_SNAPSHOT_REF` 都按设计直写账本（这是 ADR-0004"单写者=调度器"的既有例外，Phase 1 报告 §6 已核对为事实）。于是重放时会出现"某条事件确实存在、却不在任何决策的依据列表里"的现象（A6 实测中 seq 17 即缺席）。

账本全序仍然连续可重放，所以 Phase 1 验收通过；但"决策依据"字面上不完整，Phase 2 承接策略类插件后会更容易撞上（策略介入与拒绝事件更多）。

## 决策

1. **`DECISION.basedOn` 语义定为"本决策显式引用的关键事件编号"**（授权拒绝、策略裁决、失败结果等），不再声称是"决策前全部事件"。
2. **新增依据上界 `throughSeq`**：本决策之前该 run 已写入的最大事件编号。归因表述由"依据=basedOn 列举"变为"依据=basedOn 关键引用，且信息上界=throughSeq 之前的全部账本内容"——**任何直写事件都在上界之内，不再缺席**。
3. **不做全量枚举**：不把 basedOn 扩成 `[1..lastSeq]`。长跑 Run 每轮枚举全部前序编号会让账本体积按轮数平方增长，且读方本来就能按 seq 顺序拿到全部事件，枚举不带来任何新信息。
4. **兼容**：事件信封 `schemaVersion` 递增；读方对缺失 `throughSeq` 的旧事件按"无显式上界"处理（Phase 1 fixtures 与既有账本继续可读，standards/05 §2.3 格式兼容义务）。
5. 落点：Phase 2 切片⑤实现；契约 §4.1/§5 同步修订注记；A6/A7 相关测试补上界断言与"旧样例仍可读"断言。

## 理由

- 归因需求本身是"这条决策能看到什么信息"，上界游标恰好回答它；枚举列表是同一事实的低效表达。
- 保留 `basedOn` 的关键引用有独立价值：它区分"内核认为决策真正依据的那几笔"（可解释性），删掉它就退化成一个纯序号。
- 单写者例外是性能与职责的现实选择（授权/网关/追踪器在自己路径上记账最快），不因归因需求而推翻——需要的是将事实**表达清楚**。

## 后果

- 积极：审计重放不再出现"依据列表里找不到某条已发生事件"的误读；V6 主张表述更准确。
- 代价/风险：多一个事件字段（每轮 1 个整数，成本可忽略）；契约与 fixtures 需同步，Phase 2 前既有账本与新账本共存，读方必须有版本兼容分支（Phase 1 报告 §3 第 2 条限制届时关闭）。
- 重评条件：若出现"必须精确知道决策引用了哪些非关键事件"的真实审计需求（如合规逐笔取证），再评估逐笔引用方案。

## 实施注记（2026-11-03 切片⑤施工期追加；只补事实，不改上面任何一条决策）

1. **决策 2 的上界由账本在写入点盖章，不由调度器自报**。形状：`Ledger.append(ref, type, payload, { stampSeqBeforeAs: "throughSeq" })`——账本在**写队列执行期**取本 scope 的高水位写进载荷的这个键。理由是 F3：seq 本身就是在这个执行期分配的，"调用方先读一下最大 seq 再拼进载荷"会漏掉读与写之间落账的直写事件，而那正是本篇背景段要修的那类错（A6 实测的 seq 17）。盖章是类型无关的（键名由调用方给），账本仍然不知道 DECISION 是什么；`scheduler.ts` 只有那一处传 `"throughSeq"`。
2. **决策 4 的"信封 schemaVersion 递增"落在类型级**：`EVENT_SCHEMA_VERSION: Partial<Record<EventType, number>>`，`DECISION` / `MODEL_INVOKED` / `MODEL_USAGE` = 2，其余按 §5 现值 = 1，写点在 `ledger.ts` 的 `makeEvent` 一处。全局常量一枚递增会宣告**所有**事件类型都改过格式（不为真），且反证切片④给 `ASSEMBLY_RECORDED` 追加 `policies` 那次没处盖章——两处扩展由此用同一口径。这是实施层对决策 4 的补正，"递增"这条主张本身没动。
3. **稠密性哨兵**：今天每 run 单写者、`lastSeq+1` 递增，所以 `throughSeq === seq-1` 恒成立。测试把它钉成断言（`packages/core/test/ledger.test.ts` 的交错直写用例 + `tests/decision-through-seq.test.ts` 的真实 run），哪天写入面变了（分片、批量、多写者）先红，而不是让归因表述悄悄漂移。字段的可推导性因此是**登记过的事实**，不是"其实没必要加"的漏洞——价值在内核亲口声明边界，不在新信息。
4. **读方落点两处**：`keel replay` 有 `throughSeq=N` 时打数字，没有时明打 `throughSeq=(no explicit bound: pre-v2 ledger)`——审计员看得见"这是旧账本"而不是"内核漏写了"；Phase 1 的 fixtures 目录原样可读，无迁移。
